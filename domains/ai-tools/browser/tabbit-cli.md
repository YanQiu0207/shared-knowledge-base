# Tabbit CLI

## 结论

Tabbit CLI 让外部 Agent 在用户的 Tabbit 浏览器中完成任务，内部复用并适配 Playwright。按本文所据官方文章，它不是面向任意 Chrome 的通用控制工具；尚未核实其他版本是否新增独立 Chrome 接入模式。[1：§1.2、§3.1、§5.1]

## 架构与浏览器限制

| 层次 | 职责 |
| --- | --- |
| 外部 Agent | 理解、规划任务，处理新的业务判断 |
| CLI + Skill | 提交程序、查询回执，指导观察、验证和恢复 |
| Playwright 操作层 | 定位、等待、输入、可操作性检查与断言 |
| Tabbit 浏览器 | 页面访问边界、现有登录态和后台执行 |
| 浏览器托管的 Runtime Service | 跨调用状态、任务生命周期与执行回执 |

以上来自文章。[1] 浏览器侧通过私有传输通道在进程内附着页面，不开放调试端口。因此，「基于 Chromium」「使用 CDP」不意味着 CLI 可直接连接普通 Chrome；底层操作引擎可复用，不等于整套集成可脱离 Tabbit 使用。

## 值得复用的设计

1. 将已明确的连续操作与断言组织在同一段 JavaScript 中，需要新判断时再返回模型；减少往返，不省略验证。[1：§4.1]
2. `status: succeeded` 只表示程序正常结束，不等于业务提交成功，应通过断言或业务记录确认。[1：§4.3]
3. 响应丢失时先查询原回执，再核对业务状态，不盲目重复写操作；结果不确定时可返回 `OUTCOME_UNKNOWN`。[1：§5.2]
4. 同一请求 ID 只有在原任务回执仍可用时才复用已有结果，不是永久业务幂等保证；应用支持幂等键时仍需使用。[1：§4.3、§5.2]
5. 页面控制范围隔离不等于账号隔离：任务仍共享浏览器配置文件中的 Cookie 与登录账号，提示注入和敏感操作仍需要宿主与用户授权。[1：§3.2]

## 如何理解评测

文章内部对比使用 25 道题、每题重复 3 次，即每种方案 75 次配对尝试；Tabbit CLI 相比 Codex Chrome Control 的总输入 token 少 47.2%，其中包含缓存输入。[1：§6、附录]

- 不是对 BrowserSkill 或裸 Playwright 的比较。
- 正确率差异不显著；预设正确率判定门槛未通过，数字仅作描述。
- 配对耗时区间跨过 1，输出消耗更高，不能概括为全面更快、更可靠。
- 输入 token 降幅不等于账单降幅，计费仍受模型、缓存等因素影响。

本次只核读文章正文，未复核原始数据；部分图表和代码没有出现在网页提取结果中，不能视为完整复现实验。

## 使用建议

已使用或愿意使用 Tabbit 浏览器时，可评估它作为 Agent 联调与探索入口；日常使用 Chrome 时，不应仅凭这篇文章认定必须迁移。完整路由见 [对比与选型](comparison.md)。
