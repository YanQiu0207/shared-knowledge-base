# Skill 自进化：概念、工具与低成本实践

## 结论

Skill 自进化可以理解为：从任务执行与反馈中提炼可复用经验，修改外部技能资产，再通过验证决定是否采用。这里的外部资产包括技能说明、脚本与引用资料；不是所有项目都优化完整目录。[S1][S2][S3]

「生成一份 Skill」「反复改写文字」「收集大量日志」本身不等于能力提升。应区分生成、修复、效果优化与模型训练；没有任务结果对比时，只能说内容发生变化，不能说效果已提升。下文将官方机制与实践建议分别标注。

## 1. 什么在进化？

| 类型 | 更新对象 | 反馈与验证 | 本文中的对应项目 |
| --- | --- | --- | --- |
| 经验提炼 | 从轨迹生成或深化技能 | 成功、失败轨迹及后续评测 | Trace2Skill |
| 技能修复 | 说明、脚本、引用与测试 | 可复现故障、回归测试与审查 | SkillHone 日常维护 |
| 效果优化 | 技能文本或技能目录 | 固定任务、评分与候选门禁 | SkillOpt、SkillHone Benchmark |
| 模型训练 | 模型权重 | 训练目标与独立评估 | 不属于本文重点 |

前三类的机制分别见 [S1]、[S2]、[S3]；这是便于选型的分类，不是行业统一标准。技能优化可以不改变模型权重，SkillOpt 明确采用这一方式。[S1]

技能市场解决「发现与分发」，不自动证明「使用效果改善」。不要仅凭项目名称含 Skill、文章发布在某厂商社区，就认定它是该厂商的自进化平台；归属优先查官方仓库和论文作者单位。

## 2. 一个可审查的闭环

以下是结合官方机制归纳的实践模型，不是所有工具都默认具备的保证。

1. **观察**：保存任务输入、相关执行轨迹、结果与错误，不默认收集全量历史。
2. **归因**：区分技能问题、环境故障、模型波动和评测缺陷，避免错误修补。
3. **提案**：把个案提炼为适用条件明确的规则或实现补丁，只修改候选副本。
4. **验证**：先运行结构检查和已知失败案例，再检查独立案例与安全约束。
5. **采用**：人工审查差异，保存版本、验证证据和采用理由；失败候选保留记录，不覆盖原版。

例如，某次命令失败不应直接沉淀为「永远换一种工具」。先确认失败是否来自路径、编码、依赖或调用方式，再决定补规则还是修脚本。

## 3. 几家项目分别适合什么？

### 微软 SkillOpt：把技能文本当作优化状态

**官方文档确认**：研究引擎通过任务执行、轨迹反思、补丁聚合、修改与验证门禁迭代技能文档，不更新目标模型权重。自定义任务需要接入数据加载、执行评分、环境适配和配置；并非导入任意技能目录即可自动优化。[S1][S5]

**实践判断**：适合已有任务集和评分器，希望比较原版与候选版效果的场景。不要把技能文本优化能力等同于完整技能包修复能力。

SkillOpt-Sleep 是另一条预览工作流：读取支持的会话来源，提炼任务并暂存建议供审查。官方明确说明，真实后端会把会话节选和衍生任务发送给所选模型服务，不能保证提示中绝无秘密。mock 后端不调用模型服务；dry-run 不应被当作离线或不外发承诺。[S6]

### 腾讯 SkillHone：围绕完整技能包持续修复

**官方文档确认**：管理技能说明、脚本、引用、资产与测试，将故障、修复分支、运行记录、本地 PR 和决策历史关联。日常故障修复与系统性 Benchmark 优化是两条不同路径。[S2][S7]

导入时，每个 Skill 成为独立管理的 Git 仓库。copy 保留原技能，后续显式同步；takeover 备份原技能并将运行时位置链接到管理目录。review 与 automatic 是独立的合并策略，不能混为一谈。[S7]

**接入注意**：setup 会向所选 Agent 的全局指令文件加入路由规则并链接技能。不要把它视为零配置改动。原技能有跨目录相对引用时，复制后是否仍有效需要另外检查。[S7]

**评测边界**：Benchmark 路径使用分离的 Skill 与 Eval 仓库，冻结评测提交及数据指纹，区分 probe、pr_val 与 test。官方说明该组织方式不是对恶意本地进程的容器或虚拟机级隔离。[S8]

**实践判断**：适合已有技能包需要持续维护、可复现修复和历史追踪的场景。首次接入宜选择 copy 与 review，不直接接管全部技能。

### 阿里 Qwen Trace2Skill：从执行轨迹提炼技能

**官方文档确认**：分析一批成功或失败轨迹，提出局部补丁，再分层聚合为技能；支持深化已有技能与从草稿创建技能。公开仓库重点提供电子表格实现及技能，不能据此假定其他领域开箱即用。[S3]

**实践判断**：适合已经积累任务日志、希望提炼共性经验的场景；先评估轨迹质量和迁移成本，不为使用工具而大量生成日志。

### 字节 MUSE-Autoskill：技能生命周期研究

**论文确认**：作者单位包含 ByteDance；研究将技能创建、记忆、管理、评估与修订组成生命周期，并提出技能级记忆。[S4]

**证据限制**：本文未核实可直接使用的官方开源优化平台，不提供安装或可用性承诺。适合学习机制，不应直接当作现成产品推荐。

## 4. Token 紧张时如何起步？

以下为低成本实践建议，尚非本文作者实测的最佳参数。

1. 只选一个高频、结果容易判断的 Skill，不先优化核心编排或整个技能库。
2. 收集 2～3 次真实失败，只提供相关输入、输出和规则片段；保留必要上下文，防止裁剪后误归因。
3. 先使用确定性检查定位命名、引用、脚本和格式问题，不为这些问题消耗多轮模型评审。
4. 每轮只提出一个最小修补，不新增平台、配置或自动后台循环。
5. 复测已知失败，再加入未用于改写的正常和边界案例；固定模型、工具与预算。
6. 设置调用量或费用上限，以及无收益停止条件。实际 Token 以服务或宿主用量记录为准，不用字符数冒充精确 Token 数。

这条路线只适合验证具体修补是否值得采用。少量案例通过不能证明总体收益；需要更强结论时，再补足任务覆盖、重复运行和保留测试集。

## 5. 怎么判断真的变好了？

### 分开检查结构与行为

- **结构证据**：Frontmatter、文件与引用有效、脚本测试、必要规则是否保留。
- **行为证据**：真实任务是否完成、该触发时是否触发、不该触发时是否停止、是否扩大权限或修改范围。
- **成本证据**：任务级耗时、Token、调用费用和人工纠正次数；未知值保留未知。

文件更短、规则更多、输出「Using」或 JSON 格式正确，都不足以单独证明任务效果提升。这是评测解释原则，不是某工具的自动评分承诺。

### 控制评测泄漏

建议将数据分为开发、候选选择与最终测试三类。开发案例用于修改，选择集用于挑候选，最终测试仅在候选确定后使用；若看过最终测试结果又继续改写，就不能再把该组数据称为未见测试。

同一任务的改写、相近样本和共享答案也可能造成泄漏，不能只按文件名拆分。评分器、答案及安全规则不应与候选技能一起交给优化器任意修改。[S8] 提供了相关组织机制，但文件分离本身不等于强安全隔离。

比较无技能、原版与候选版有助于区分技能收益与修改收益；预算不足时，可以先只比较原版与候选版，但应缩小结论，不声称已证明技能相对无技能的净收益。

## 6. 安全与维护边界

以下为实践建议：

- 只发送必要且脱敏的任务材料；本地保存不等于模型调用时不外发。
- 默认候选副本、人工审查和显式采用，不自动覆盖原版或推送。
- 将批准要求、安全边界、失败停止和证据要求设为不可削弱约束。
- 需要机器判定的规则优先接入检查，不只追加自然语言提醒。
- 失败经验必须带适用条件，避免把一次环境故障变成永久禁令。
- 跨项目条目只保留泛化机制；业务数据、私有日志、密钥和项目专属门禁留在受控项目中。
- 保存来源、版本与验证范围；后续证伪时标记退役和替代条目，不删除历史。

## 7. 选型速查

| 当前问题 | 建议先做 | 何时考虑工具 |
| --- | --- | --- |
| 少量明确错误，Token 紧张 | 单点归因、最小修补与小规模复测 | 暂不引入平台 |
| 有任务集，希望量化优化技能文本 | 固定执行与评分合同 | SkillOpt |
| 脚本、引用、说明持续失效 | 建立故障复现、回归与审查 | SkillHone |
| 有较多高质量执行轨迹 | 筛选可泛化经验并验证 | Trace2Skill |
| 想从历史会话持续学习 | 先明确隐私与预算边界 | 审慎评估 SkillOpt-Sleep |
| 研究完整技能生命周期 | 阅读原始论文、区分研究与产品 | MUSE-Autoskill |

本表是机制适配判断，不是性能排名，也不代表本地运行验收。
