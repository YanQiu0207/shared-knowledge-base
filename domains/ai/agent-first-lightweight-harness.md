# Agent 优先编码的轻量 Harness 演进

## 结论

模型能力提升不会使 Harness 消失，而是会让「为补偿旧模型短板而固化的编排」更容易过时。跨项目可复用的默认路线是「原生 Agent 优先、仓库环境为主、编排按风险启用」：

1. 先让 Agent 获得清晰目标、相关上下文、约束和完成条件。
2. 将重复出现的错误转成测试、Lint、结构检查、文档或工具反馈，而不是持续增加 Prompt 和审批步骤。
3. 只有在并行写入、长任务恢复、跨宿主兼容、审计或高风险变更有明确收益时，才启用 worktree、任务 DAG、状态账本、能力探测等编排机制。
4. 任何补偿模型局限的机制都应定期重评；若原生 Agent 已能稳定完成，或没有真实任务数据证明净收益，就退出默认路径。

这不是「取消验证」：应保留与真实风险直接对应的测试、Lint、类型检查、行为验证和一次聚焦的最终审查。

## 官方资料的共同原则

OpenAI 的 Harness Engineering 文章将人的职责放在目标、验收标准、架构边界和反馈回路，将 Agent 的职责放在执行。它强调仓库应成为 Agent 可发现、可验证、可修改的记录系统；短小的 `AGENTS.md` 应作为地图，深层规则与事实放进可索引文档。

Codex 最佳实践给出渐进式采用顺序：先提供任务上下文和完成条件；复杂任务先规划；重复有效的规则再写入 `AGENTS.md`；重复流程稳定后才封装 Skill 或自动化；MCP 只接入能消除实际手工环节的外部能力。

两篇资料均不支持把复杂编排、工具接入或多 Agent 协作当作每项任务的默认前置条件。

## 默认能力阶梯

| 层级 | 采用条件 | 应保留的能力 | 不应预先建设的能力 |
| --- | --- | --- | --- |
| 原生执行 | 任务边界清晰、单 Agent 可完成、风险低 | 目标、上下文、约束、完成条件；相关测试与 diff 审查 | 任务 DAG、状态机、跨宿主 Adapter |
| 仓库反馈 | 同类错误反复出现，或 Agent 缺少可观察反馈 | 可执行测试、Lint、结构检查、日志或浏览器验证 | 通用监控平台、无关联的 MCP 集成 |
| 稳定复用 | 工作流已经多次手工验证有效 | 短小 Skill、局部 `AGENTS.md`、自动化脚本 | 覆盖所有边界条件的巨型 Skill |
| 编排与审计 | 并行写入、长任务恢复、跨产品协作、高风险或合规要求 | worktree、有限任务依赖、结构化交付证据、独立审查 | 对普通任务强制能力探测、运行账本或多 Agent 调度 |

## 设计准则

### 任务合同先于流程合同

每项任务至少明确四项：

- 目标：要改变或构建什么。
- 上下文：相关代码、文档、示例、错误或运行信息。
- 约束：架构、安全、兼容性和工程规范。
- 完成条件：通过哪些测试、行为变化或验收证据确认完成。

如果四项已清楚，优先让原生 Agent 直接执行；仅在任务本身存在不确定性或高风险时增加计划和协调阶段。

### 用确定性反馈替代重复提示

当同一类错误再次出现时，优先判断能否转为机器可执行反馈：

- 行为错误：补回归测试或可复现实例。
- 架构漂移：补依赖规则、结构测试或定制 Lint。
- 缺少上下文：补仓库内文档索引、示例或运行入口。
- 缺少观测：为实际调试路径提供日志、指标、追踪或浏览器验证。

不能可靠机械判断的事项，保留人工验收或一次独立审查；不要伪装成确定性门禁。

### 将知识设计为地图，而非手册

根 `AGENTS.md` 只保存项目地图、常用验证命令、关键约束和深层文档入口。模块级规则靠近代码放置，复杂设计和计划独立存档。规则应在真实摩擦出现后追加，并定期清理已过时内容。

## 引入与退役检查

引入新 Harness 能力前，回答：

1. 它解决过哪些真实、重复的问题？
2. 原生 Agent、现有测试或现有工具为何不能解决？
3. 它增加了哪些 Token、时延、维护和兼容成本？
4. 用哪些真实任务指标判断它值得保留？

出现下列任一信号时，应降级或退役默认启用：模型升级后原生能力已覆盖；机制仅复述 Prompt 约束；缺少真实任务的质量或效率增益；维护协议本身已成为主要故障来源。

## 边界

- OpenAI 的高吞吐、Agent 自主合并和内部观测栈是特定组织实践，不能直接外推到个人项目或所有团队。
- 「工作流稳定后再自动化」不等于放弃高风险控制；安全、数据迁移、生产发布和合规场景仍需按实际风险增加人工确认与审计。
- 本条目的「默认路线」是方法建议，不是模型能力的受控对比结论；接入新模型、宿主或项目时，应以同类真实任务验证。
