# 从实体到模块划分

## 结论

实体清单到模块图之间有一条四步管道：**列实体 → 按生命周期驱动源初分组 → 裁决争议实体 → 三项检验**。分组的核心判据只有一句话：**一起变化的放一起，不变量不跨界**——由同一组业务动作驱动增删改的实体属于同一个模块，守护同一个不变量所需的数据必须在同一个模块内。

本方法服务于[中小型后端项目系统设计方法论](methodology.md)的阶段 2。

## 输入形态

阶段 1 的产出：用户故事清单 + 从故事里圈出的名词（候选实体）和动词（候选动作）。

## 四步管道

### 第 1 步：列实体和动作

把阶段 1 圈出的名词逐个过一遍，剔除两类：纯属性（「余位」是排期的属性还是独立实体？先存疑，留给第 3 步）和 Won't 范围的概念。动词按「谁发起」标注主体。

### 第 2 步：按「生命周期驱动源」初分组

对每个实体问同一个问题：**它的创建、修改、终结由哪一组业务动作驱动？**

驱动源相同的实体归入同一组，每组就是一个候选模块。这是两条经典原则的实用合并：

- Parnas 信息隐藏（1972）：按「可能一起变化的设计决策」切模块，而不是按处理流程
- 共同闭包原则（CCP，Robert C. Martin）：因同一原因、在同一时间变化的东西放在一起

辅助判断的**词汇表测试**（限界上下文的本义）：同一个词在不同语境下含义不同，就是模块边界的信号——「用户」在账户语境里是「手机号 + 身份 + 会话」，在预约语境里只是一个被引用的 ID。

模块数量经验值：中小型项目 3–6 个。只切出 1–2 个说明没有边界，超过 8 个说明切碎了。

### 第 3 步：裁决争议实体

初分组后总有几个实体两边都想要，用三个判据按顺序裁决：

1. **不变量就近**：这个实体参与守护哪个不变量？守护同一个不变量需要原子更新的数据，必须落在同一个模块（这是 DDD 聚合思想的轻量化：一致性边界即模块边界的下限）
2. **消环**：分别假设它归属两边，画出依赖箭头——哪种归属产生循环依赖，就排除哪种
3. **变更原因**：想象两三个最可能的未来需求，它跟着谁一起改？

### 第 4 步：三项检验

1. **依赖无环**：出现环不是「加个中间层」能解决的，是某个实体放错了模块，回第 3 步
2. **故事映射**：每个用户故事能指出主模块；一个故事要横跨 3 个以上模块，边界可疑
3. **一句话职责**：说某模块职责时需要用「和」连接两件不相关的事，拆

## 常见错误对照表

| 错误 | 症状 | 修正 |
| --- | --- | --- |
| 按技术层划分 | 「controller 模块、service 模块、dao 模块」 | 模块是按业务能力的垂直切分；分层是水平的，发生在每个模块内部 |
| 按页面划分 | 「首页模块、我的模块」 | 页面是视图组合，多个页面共享同一业务能力 |
| 一个实体一个模块 | user 模块、course 模块、schedule 模块…… | 判据是生命周期驱动源，不是表的数量；课程和排期同生共死，归一个模块 |
| 万能 common 模块 | 说不清归属的实体都塞进去 | 每个实体必须有唯一归属；工具代码不是业务模块 |
| 不变量跨模块 | capacity 在 A 模块、booked_count 在 B 模块 | 不变量需要的数据必须同模块原子守护 |

## 完整推导演示：FitBook

### 第 1 步：实体清单

来自阶段 1 的名词：用户（会员 / 管理员）、会话、验证码、课程、教练、排期、余位、预约、候补、通知任务。次卡属于 Won't，剔除。「余位」疑似排期的属性，存疑待裁决。

### 第 2 步：按驱动源初分组

| 实体 | 增删改由什么动作驱动 | 候选模块 |
| --- | --- | --- |
| 用户、会话、验证码 | 注册、登录、登出 | account |
| 课程、教练、排期 | 管理员排课、停课 | catalog |
| 预约、候补 | 会员约课、取消、递补 | booking |
| 通知任务 | 业务事件产生、定时投递消费 | notification |

预约和候补为什么不拆开？递补逻辑让它们总是在同一个事务里一起变化——共同闭包。

通知为什么不并入 booking（任务明明是它产生的）？变更原因测试：换短信服务商、调重试策略，都与预约规则无关；而且取消排期（catalog 侧动作）将来也要发通知——多个生产者，一个消费逻辑，独立成模块。

### 第 3 步：裁决争议实体

**余位（booked_count）——本项目最重要的一次裁决**：

- US-2 浏览课表要显示它（catalog 侧），US-3 预约要扣减它（booking 侧），两边都想要
- 假设归 booking：catalog 显示余位需要查 booking 的数据 → `catalog → booking`；而 booking 校验排期状态和开课时间需要 catalog → `booking → catalog`——**出环**
- 假设归 catalog（作为排期的属性）：booking 通过 catalog 提供的「占用 / 释放名额」操作扣减 → 只有 `booking → catalog` 单向——无环
- 再用不变量就近验证：「不超订」需要 capacity 和 booked_count 原子比较更新，归 catalog 后两者同表，一条条件 UPDATE 即可守护
- 裁决：归 catalog。消环和不变量就近两个判据指向同一个答案

**教练**：会员眼里是课程的属性，管理员眼里是排课的输入。本期教练不登录（数据角色）→ 归 catalog。预判演进：若未来做教练端（登录、管理自己的课），教练的**身份**部分移入 account，catalog 保留引用——裁决时顺手写下这句话，就是未来的演进路标。

**预约名单（US-6）**：管理员的功能，直觉想放 catalog（管理端嘛）。但名单只是预约数据的一个查询视图——**数据归属决定功能归属**，由 booking 提供管理端查询接口。「管理端」是权限维度，不是模块维度。

### 第 4 步：三项检验

- 依赖图：booking → catalog、account、notification，其余互不依赖，无环 ✓
- 故事映射：全部 11 条故事各有主模块（见示例 02 文档的映射表）；US-7 横跨 catalog 与 booking，但两个守护点各自单一，已在边界备注中写明 ✓
- 一句话职责：四个模块均无「和」式职责 ✓

最终产物见[示例项目的模块图](example-fitbook/02-domain-model.md)。
