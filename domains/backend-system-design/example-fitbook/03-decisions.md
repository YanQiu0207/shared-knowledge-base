## ADR-001: 放课瞬间的防超订机制

- 状态: 已接受
- 日期: 2026-07-12

### 背景

US-7 要求任何并发下不可超订。NFR：抢课写峰值约 100 QPS、持续约 1 分钟，热门课容量 20–50 人。这是全项目唯一的并发热点。

### 决策

纯数据库方案，单库事务内完成：

1. 余位扣减用条件更新：`UPDATE schedules SET booked_count = booked_count + 1 WHERE id = ? AND booked_count < capacity`，影响行数为 0 即满员
2. 预约表 `(schedule_id, user_id)` 唯一约束防重复预约
3. 排期表加 `CHECK (booked_count <= capacity)` 作最后防线

### 备选与放弃原因

- Redis 预扣减 + 异步落库：100 QPS 远在单库能力内（单行条件更新可承受数千 TPS），引入 Redis 平添缓存与库的一致性对账成本
- 消息队列排队削峰：同理，命中反过度设计清单「没有真实削峰需求，不上」

### 后果

- 收益：零新增组件，强一致，代码量最小
- 代价：极端热点下存在行锁竞争，100 QPS 量级可忽略
- 重新评估信号：放课峰值超过约 2000 QPS，或出现分库部署需求

## ADR-002: 认证方案

- 状态: 已接受
- 日期: 2026-07-12

### 背景

会员用手机号 + 验证码登录（US-1），管理端与会员端同一套后端。单实例部署。

### 决策

不透明 token + 服务端 `sessions` 表：登录成功后生成随机 token 存库，请求经 `Authorization: Bearer <token>` 携带，中间件查表校验。

### 备选与放弃原因

- JWT：无状态、省一次查库，但吊销困难（踢下线、封号需要额外黑名单机制）且引入密钥管理；本项目峰值 300 QPS，sessions 表索引查询毫无压力，无状态的收益不存在

### 后果

- 收益：实现最朴素，天然支持吊销与踢下线
- 代价：每个请求多一次索引查询（可接受）
- 重新评估信号：session 校验查询成为实测瓶颈时再评估 JWT 或缓存

## ADR-003: 通知投递方式

- 状态: 已接受
- 日期: 2026-07-12

### 背景

US-9 要求预约成功、候补递补、课程取消时通知会员，时效分钟级即可。第三方短信 / 微信接口可能抖动，不能拖垮预约主流程。

### 决策

事务性发件箱的最简实现：booking 在业务事务内向 `notification_tasks` 表写入任务；notification 模块内一个定时任务每 30 秒轮询待发任务，调第三方接口投递，失败退避重试 3 次后标记死信。

### 备选与放弃原因

- 消息队列：命中反过度设计清单「没有真实的异步削峰或多消费者需求，不上」；通知量峰值约每分钟百条，轮询绰绰有余
- 业务事务内同步调用第三方：第三方超时会直接拖垮预约接口，违反延迟 NFR

### 后果

- 收益：通知不丢（与业务同事务落库）、延迟 ≤ 30 秒满足分钟级要求、任务表天然是审计日志
- 代价：最多 30 秒投递延迟；轮询空转（单库上成本可忽略）
- 重新评估信号：通知量超过每分钟数千条，或出现多个消费方需要订阅业务事件
