# 阶段 5：实现与演进

## 骨架切片（walking skeleton）

第一步不是铺功能，而是打通一条最小的端到端链路并完成部署：

- 选择的切片：`GET /api/v1/schedules?date=`——HTTP 路由 → catalog 应用层 → PostgreSQL 查询 → JSON 返回
- 附带完成:项目分包结构（四个模块的目录骨架）、数据库迁移机制、Docker Compose（应用 + PostgreSQL）、一条端到端测试
- 选它的原因：只读、暂不依赖鉴权，却能一次验证项目结构、数据库连通和部署流程三件事

后续铺功能的顺序按依赖方向：account（鉴权中间件）→ booking 核心事务（US-3 / US-4 / US-7，本项目风险最高的部分，尽早写并发测试）→ waitlist → notification。

守护测试清单（骨架期就写好，之后每次改动预约相关代码都必须通过）：

1. **并发抢课**（US-7 / ADR-001）：对容量为 N 的排期发起 10 × N 个并发预约，断言成功数恰为 N 且 `booked_count = N`
2. **重复取消**：对同一预约并发发起多次取消，断言候补只被递补一人、`booked_count` 一致
3. **取消排期竞态**：取消排期与取消预约并发执行，断言最终无幸存的 confirmed 预约，且每位受影响会员恰有一条通知任务
4. **验证码防爆破**：同一验证码连错 5 次后，提交正确验证码也被拒绝；登录成功后重放同一验证码失败

## 演进推演：三个月后新增「第二家门店」

演示方法论第 5 阶段的规则——每次新需求先回阶段 2 检查模块边界。

1. **回阶段 2**：「门店」是新名词。排期发生在具体门店 → 归 catalog；会员是否分门店？业务上会员全店通用 → account 不动。结论：catalog 新增门店实体，schedules 加 `store_id`；booking 只认 `schedule_id`，完全不受影响。**模块边界稳定，不需要重新划分。**
2. **回阶段 4**：API 上 `GET /schedules` 增加 `store_id` 查询参数；数据上新增 `stores` 表，`schedules` 加 `store_id NOT NULL` 并为存量数据回填默认门店。
3. **是否需要 ADR？** 不需要——未偏离任何默认答案，只是既有模块内的实体扩展。不是所有变化都值得一条 ADR，这个判断本身就是方法论的一部分。

同时做反过度设计自查：两家门店不构成拆微服务或分库的信号（NFR 数字翻倍后仍远在单库能力内）。
