# 中小型后端项目系统设计方法论

## 结论

一套五阶段设计流水线：需求澄清 → 领域建模 → 架构选型 → 接口与数据设计 → 实现与演进。总设计投入 2–4 天，产出 4 类工件：需求一页纸、模块图、ADR、API 契约。

核心原则只有一条：**默认采用最朴素的方案，任何偏离默认的决策必须有阶段 1 的 NFR 数字支撑，并写 ADR。**

## 适用范围

- 1–5 人团队或个人项目，单体应用可承载的流量（新产品验证、内部工具、中小型业务系统）
- 不适用：明确的高并发、大数据量场景（此类需基于《数据密集型应用系统设计》做专项设计）

## 总览

| 阶段 | 时间盒 | 产出物 | 完成标准 |
| --- | --- | --- | --- |
| 1 需求澄清 | 0.5–1 天 | 需求一页纸 | 功能需求可验证，NFR 有数字 |
| 2 领域建模 | 0.5 天 | 模块图 | 用户故事可映射到模块，依赖无环 |
| 3 架构选型 | 0.5 天 | ADR 若干 | 难改的决策要么是默认答案要么有 ADR |
| 4 接口与数据 | 1–2 天 | API 契约 + 数据模型 | 调用方拿契约能 mock，建表 SQL 能直接导出，写操作幂等与竞态有答案 |
| 5 实现与演进 | 贯穿开发期 | 骨架切片、增量 ADR | 每次扩展不推翻既有模块边界 |

## 阶段 1：需求澄清

动作：

1. 功能需求写成用户故事（作为 X，我要 Y，以便 Z），按 MoSCoW 分级（Must / Should / Could / Won't）
2. 非功能需求填硬指标表，没有精确数字就给量级估计
3. 做三行容量估算：用户数 → 请求量 → 存储量
4. 写明「不做什么」（范围栅栏）

从原始需求（一句话想法、痛点抱怨）推导用户故事的具体方法，见[从原始需求到用户故事](requirements-to-user-stories.md)。

NFR 硬指标表模板：

| 指标 | 要回答的问题 | 示例答案 |
| --- | --- | --- |
| 用户规模 | 一年后有多少用户 | 1 万注册，1 千日活 |
| 峰值 QPS | 最热接口峰值多少 | 小于 100 |
| 数据量 | 一年后最大的表有多少行 | 百万级 |
| 可用性 | 停机一小时会损失什么 | 内部工具，可接受 |
| 一致性 | 哪些操作绝对不能出错 | 支付、扣库存 |
| 延迟 | 用户可感知接口的目标 | P95 小于 300ms |

完成标准：每条功能需求可验证；每条 NFR 有数字或明确标注「无要求」。

经验法则：中小型项目的 NFR 答案大多是「单机 + 单库就够」——把这个结论写下来，它是后续所有反过度设计判断的依据。

## 阶段 2：领域建模

来源：DDD 战略设计的轻量化（Eric Evans《领域驱动设计》，2003）。只取限界上下文思想，不使用聚合、值对象等战术模式——中小型项目用不到，成本大于收益。

动作：

1. 从用户故事里圈名词（候选实体）和动词（候选操作与事件）
2. 按「实体的生命周期由谁管理」把实体分组成模块，每个模块写一句话职责
3. 画模块依赖图：箭头单向，禁止环；出现环说明边界划错了
4. 把每个用户故事映射到模块，映射不了的回头调整边界

从实体清单推导模块划分的具体方法（分组判据、争议实体裁决），见[从实体到模块划分](entities-to-modules.md)。

完成标准：任一用户故事能指出主要落在哪个模块；依赖图无环。

## 阶段 3：架构选型与决策

默认答案（不写理由，直接采用）：

- 模块化单体，代码按阶段 2 的模块分包
- 关系型数据库（PostgreSQL 或 MySQL）
- 同步 HTTP API
- 模块内分层：接口层 → 应用层 → 领域层，基础设施依赖倒置，依赖方向永远指向领域层（六边形架构思想，Alistair Cockburn「Ports and Adapters」）
- 部署：单实例 + 托管数据库

偏离默认必须写 ADR（Michael Nygard「Documenting Architecture Decisions」，2011）。典型需要 ADR 的决策：改用 NoSQL、引入消息队列、引入缓存、拆分服务、认证方案、框架选型。

ADR 模板：

```markdown
# ADR-001: <决策标题>

- 状态: 已接受 | 已废弃 | 被 ADR-xxx 取代
- 日期: YYYY-MM-DD

## 背景
<什么问题逼出了这个决策，约束是什么>

## 决策
<选了什么>

## 备选与放弃原因
<至少一个备选方案，以及为什么不选>

## 后果
<收益 + 代价 + 出现什么信号时需要重新评估>
```

完成标准：每个「以后难改」的选择，要么是默认答案，要么有一条 ADR。

## 阶段 4：接口与数据设计

API 先行：

1. 全局约定先定一次：错误响应结构、分页方式、鉴权方式、幂等策略、版本策略
2. 每个接口写契约（OpenAPI，或简化为接口表：方法、路径、入参、出参、错误码）
3. 用契约反查需求覆盖度：每个 Must 级用户故事都有对应接口

数据模型：

1. 每个模块画 ER 草图
2. 每张表标注：主键、唯一约束、外键、预期行数、按查询模式设计的索引
3. 全局统一决定：软删除策略、created_at / updated_at 规范、枚举的存储方式
4. 写路径专项检查——每个写操作回答两个问题：
   - **重复执行会怎样？** 客户端重试、并发重复请求下必须幂等；一次性状态转换用条件更新守护（`WHERE status = '旧状态'`，影响行数为 0 即幂等返回）
   - **与谁竞态？** 列出可能交错执行的写路径（含级联类操作，如「取消单条」与「批量取消」），用统一加锁顺序消除死锁和交错漏网；跨表的级联变更与关联的通知 / 任务写入必须同一事务

完成标准：调用方拿契约能直接 mock；建表 SQL 能从设计直接导出；每个写操作的幂等与竞态答案写在数据设计文档里。

数据设计的权威参考：Martin Kleppmann《数据密集型应用系统设计》（2017）。中小型项目通常只需其数据模型与事务章节。

## 阶段 5：实现与演进

1. 骨架先行（walking skeleton）：先打通一条最小端到端垂直切片——一个真实接口从 HTTP 进、到数据库、再返回，含部署流程——再横向铺功能
2. 每次新需求先回阶段 2 检查模块边界；边界需要变化时先改模块图，再写代码
3. 决策变化时追加新 ADR，不修改旧 ADR（旧的标记「被取代」）

反过度设计清单——出现以下冲动时，先回看阶段 1 的 NFR 数字是否支持：

| 冲动 | 默认判定 |
| --- | --- |
| 拆微服务 | 单体内模块边界还没被证明稳定，不拆 |
| 上消息队列 | 没有真实的异步或削峰需求，不上 |
| 加缓存 | 没有量化的慢查询证据，不加 |
| 分库分表 | 单表未到千万行量级，不做 |
| 做「可插拔、可配置」 | 没有第二个真实使用方，不做 |

依据：YAGNI 原则与「Monolith First」（Martin Fowler，martinfowler.com，2015）。

## 裁剪规则

| 项目类型 | 执行范围 |
| --- | --- |
| 一周内的玩具或验证项目 | 只做阶段 1 的功能清单 + 阶段 4 的全局 API 约定 |
| 标准中小型项目 | 全套，设计投入 2–4 天 |
| 预期高增长项目 | 全套 + 容量估算精细化 + DDIA 数据设计专项 |

## 与 DDD 的关系

本方法论从 DDD 中取三样、弃一样：

- **取**限界上下文（战略设计）——阶段 2 模块划分的理论基础
- **取**四层分层的词汇（接口 / 应用 / 领域 / 基础设施），但依赖方向不用 Evans 原版的自上而下（原版中领域层可依赖基础设施层），改用六边形 / 整洁架构的依赖倒置：领域层零依赖，基础设施实现领域层定义的接口。这也是《实现领域驱动设计》（Vaughn Vernon，2013）之后 DDD 社区的主流实践
- **借**聚合的核心思想「不变量即一致性边界」——阶段 2 的裁决判据「不变量就近」是它的轻量化，但不使用聚合的完整形式
- **弃**战术模式全家桶（实体、值对象、仓储、领域服务、领域事件的完整实现）——中小型项目中其抽象成本大于收益

## 来源

- Eric Evans《领域驱动设计》（2003）——限界上下文
- Martin Fowler「MonolithFirst」（martinfowler.com，2015）——单体优先
- Alistair Cockburn「Hexagonal Architecture (Ports and Adapters)」——依赖方向
- Michael Nygard「Documenting Architecture Decisions」（2011）——ADR
- Martin Kleppmann《数据密集型应用系统设计》（2017）——数据设计
- Simon Brown「C4 model」（c4model.com）——需要更正式的分层架构图时选用
