# 从原始需求到用户故事

## 结论

原始需求（一句话想法、痛点抱怨、口头描述）到用户故事之间有一条五步管道：**圈角色 → 走旅程 → 痛点反查 → 格式化质检 → MoSCoW 分级**。用户故事不是凭空「写」出来的，是沿着角色的使用旅程「走」出来的。

本方法服务于[中小型后端项目系统设计方法论](methodology.md)的阶段 1。

## 输入形态

原始需求通常是这样的东西，不要期待更规整的输入：

- 一句话想法：「我想做个约课小程序」
- 痛点抱怨：「微信群接龙太乱，经常超订」
- 竞品指认：「像 XX 那样，但要简单点」

管道的作用就是把这类输入变成可分级、可验收的故事清单。

## 五步管道

### 第 1 步：圈角色

问四个问题，把所有会碰系统的人翻出来：

1. 谁直接受益？（终端用户）
2. 谁维护数据？（管理员、运营——最容易被遗漏的角色）
3. 谁付钱？（决策者的诉求往往和用户不同）
4. 出了问题谁被骂？（他的诉求就是约束和报表）

被提及但不操作系统的人（如本期不登录的教练）记为「数据角色」，不产生故事，但会出现在别人的故事里。

### 第 2 步：走旅程

对每个角色，按时间线从头走一遍他与系统的完整生命周期：

> 第一次接触 → 建立身份 → 完成核心动作 → 情况有变 → 再次回来

每个停留点是一条候选故事。走主干之后走分支——在每个节点问「**如果……怎么办**」：

- 想要的东西没有了怎么办？（→ 候补类故事）
- 计划变了怎么办？（→ 取消类故事）
- 他怎么知道结果？（→ 通知类故事）

分支提问是异常路径故事的主要来源，只走主干会漏掉一半故事。

### 第 3 步：痛点反查

回到原始输入，把每个痛点、每句抱怨列成一行，检查它能否指到至少一条已有故事。指不到的有两种可能：

- 漏了故事 → 补
- 它不是任何角色「想要」的，而是系统必须保证的 → 记为**系统约束**（如「不可超订」），格式上标注（系统约束），与用户故事并列管理

### 第 4 步：格式化与质检

每条候选套模板：**作为 X，我要 Y，以便 Z**（Connextra 模板）。然后逐条做三项检查——这是 INVEST 原则（Bill Wake，2003）的实用简化：

| 检查 | 不通过的症状 | 处理 |
| --- | --- | --- |
| 说得出「以便 Z」吗 | 「我要一个课表页面」——这是解决方案不是需求 | 追问为什么，直到挖出目的：「以便决定约哪节课」 |
| 只有一个动作吗 | 「我要预约和取消课程」 | 拆开——两者的验收标准和边界规则完全不同 |
| 写得出可观察的验收标准吗 | 「系统要好用」 | 太模糊，继续追问到可测量为止；验收只写可观察结果，不写实现方式 |

### 第 5 步：MoSCoW 分级

判断标准一句话：**砍掉它，系统还成立吗？**

- **Must**：砍掉则核心闭环断裂（没有「预约」就不是预约系统）
- **Should**：砍掉能上线，但很快会被抱怨（没有候补，会员会打电话问）
- **Could**：锦上添花，排期富余才做
- **Won't**：明确写下来。「不做什么」和「做什么」同样重要，它是防范围蔓延的栅栏

## 常见错误对照表

| 错误 | 症状示例 | 修正 |
| --- | --- | --- |
| 把解决方案当故事 | 「我要一个搜索框」 | 追问以便什么 →「我要按教练筛课，以便只看喜欢的教练」 |
| 故事太大 | 「我要管理课程」 | 按动作拆：创建课程、创建排期、取消排期各一条 |
| 只写主角色 | 清单里只有终端用户 | 用第 1 步的四个问题把管理员、运营翻出来 |
| 只写正常路径 | 没有满员、取消、失败场景 | 第 2 步的分支提问「如果……怎么办」 |
| 验收标准写成实现 | 「用行锁保证不超订」 | 只写可观察结果：「并发预约下成功数 ≤ 容量」 |

## 完整推导演示：FitBook

原始输入（店主原话）：

> 「现在会员约课都在微信群接龙，太乱了。经常有人约了不来，也有课超了人数，教练还得自己数人头。想要个小程序，让会员自己约课、自己取消，我这边能排课、能看名单。」

**第 1 步圈角色**：会员（受益者）、店主 / 管理员（维护数据 + 付钱 + 被骂）、教练（被提及但不操作 → 数据角色，点名动作归管理员）。

**第 2 步走旅程**：

| 角色 | 旅程节点 | 产出故事 |
| --- | --- | --- |
| 会员 | 第一次使用，建立身份 | US-1 注册登录 |
| 会员 | 看有什么课 | US-2 浏览课表 |
| 会员 | 核心动作：约课 | US-3 预约 |
| 会员 | 分支：计划变了怎么办 | US-4 取消 |
| 会员 | 分支：想约的满了怎么办 | US-8 候补 |
| 会员 | 分支：怎么知道结果 | US-9 通知 |
| 管理员 | 开店配置 | US-5 创建课程与排期 |
| 管理员 | 上课点名 | US-6 预约名单 |
| 管理员 | 分支：临时停课怎么办 | US-5 的取消排期 + 触发 US-9 |

**第 3 步痛点反查**：

| 原话痛点 | 对应 |
| --- | --- |
| 「课超了人数」 | 没有角色「想要」它 → 系统约束 US-7 |
| 「教练数人头」 | US-6 |
| 「接龙太乱」 | US-2 + US-3 |
| 「约了不来」 | US-4 降低正当取消的成本；根治靠次卡计费 US-10（Could） |

**第 4 步质检示例**：原话「让会员自己约课、自己取消」含两个动作 → 拆成 US-3 与 US-4；「能看名单」缺主语和目的 → 补全为「作为管理员，我要查看某节课的预约名单，以便上课点名」。

**第 5 步分级示例**：US-8 候补砍掉能上线，但满员课会把会员逼回微信群 → Should；US-10 计费不影响预约闭环 → Could；在线支付涉及资质与对账、本期明确不碰 → Won't。

最终产物见[示例项目的需求一页纸](example-fitbook/01-requirements.md)。

## 来源

- Connextra 用户故事模板（「As a … I want … so that …」，约 2001 年，源自 Connextra 公司实践）
- Bill Wake「INVEST in Good Stories, and SMART Tasks」（2003）——好故事的六项标准
- Mike Cohn《User Stories Applied》（2004）——用户故事实践
- Jeff Patton《用户故事地图》（2014）——本方法第 2 步「走旅程」是其轻量化
